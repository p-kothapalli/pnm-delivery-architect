Discover before you name

No provider anchor, prefix, status model or lifecycle is assumed. Thirteen discovery dimensions establish how this organisation actually works, and every name in the output carries a provenance label.

Product first, then build

Shipped PNM capability is rung zero. Configuration, Flow, OmniStudio, LWC, Apex and Data 360 follow in order — and the volume class decides early, before a roster gets built as a record-by-record flow.

The architect keeps the judgment

The skill asks five to sixteen phased questions, then drafts. Scope, compliance posture, block-versus-warn and the credibility of the estimate stay with the people accountable for them.

Honest about what it could not verify

A missing tool is never evidence that a component or feature does not exist. When an org query, source search or documentation lookup is unavailable, the skill says so, labels the fact [Assumed — confirm], and raises it as a Clarification Question instead of guessing.

Why It Exists

Provider network projects fail on the same three things — and they surface in claims, not in sprint review.

01

Every Org Looks Different Inside

One payer anchors providers on the product's provider object, another on person accounts, a third on a custom object. Status may be a flag, an effective date, a picklist — or all three. A story copied from the last engagement brings the last engagement's names.

02

"And Related Records Are Updated"

Participation lives at a grain — practitioner, location, network, child network, tier, dates. Leave one row unspecified and it shows up months later as a claim denial or a directory listing for a location the provider left.

03

Volume Decides Too Late

A roster of twenty thousand rows or a tax-ID change across five hundred locations gets designed as a screen flow, because nobody stated the volume class before choosing the build technology.

An ungrounded story is a guess with acceptance criteria attached. It reads well, it estimates cleanly, and it is wrong about the one organisation it was written for.

The Shift

PNM delivery doesn't need more templates. It needs the org discovered first and the build made visible.

Before anyone writes a Given/When/Then line, the team should know where a provider's identity lives, how a record becomes effective, and — on every control in the prototype — whether it is shipped PNM, configuration or something we have to build.

Today

Stories written from memory of a previous org. Personas drift to "as a user", provider records are "updated as needed", the build technology is chosen after the estimate, and compliance evidence is an afterthought for the credentialing team to backfill.

PNM Delivery Architect

Org Discovery first, labelled findings, product-first build decision, volume class stated, Compliance & Audit where credentialing is in scope, downstream consumers listed — and every record write specified field by field.

STEP 1 · Org Discovery

Thirteen questions the skill answers before it designs

Depth follows the mode: full for new features, plans and epics; full plus the legacy side for migration; scoped to the component for refactor, bug fix and remediation. Highlighted dimensions are always resolved for new work.

D-1
Provider anchor

Where does a provider's identity live — product provider object, accounts, an application record, custom?

D-2
Identifier model

How NPI, tax ID, licence and legacy IDs are stored and historised.

D-3
Location model

How practice and billing locations are represented.

D-4
Participation model

The grain of network participation, and what automation derives.

D-5
Status & temporal model

How a record becomes effective, active, suspended or terminated.

D-6
Work model

Cases, queues, work guides and routing — who owns the work and returns.

D-7
History & audit

Field history, audit trail, custom history objects.

D-8
Naming & conventions

The discovered prefix and layering rules — or none, if greenfield.

D-9
Build technology in use

What already implements PNM behaviour, active versions only.

D-10
Licences & features

PNM add-on, Data 360, Shield, Experience Cloud, Agentforce.

D-11
Volumes

Typical and peak submissions, roster sizes, rows per transaction.

D-12
Integrations & consumers

What feeds in, and what reads provider data downstream.

D-13
Compliance scope

Accreditation, delegation and state or federal program rules.

Every name carries one of five labels

[Product] [Discovered] [Adapter] [Proposed] [Assumed — confirm]

Labels appear in the Org Discovery Context, Technical Implementation, record specifications and on custom prototype elements — never inside Given/When/Then lines.

The hard blockers — an artifact does not ship without these
1

Concrete business persona

Credentialing Specialist, Network Configuration Specialist, Provider Data Specialist. Never "user" or "system". Providers are the subject of the work, not the login role — except in genuine portal stories.

2

Business-language GWT

Explicit Given / When / Then, one When, observable Then. No API names, class names, queries, step numbers or picklist API values inside a criterion.

3

Pattern E on every write

Every "records created or updated" outcome lists each object and every field, parents before children — with temporal and status values where they apply. Never "etc."

4

Discovery and compliance

Org Discovery Context at the top; Compliance & Audit wherever credentialing, committee, delegation, monitoring or termination is in scope.

What a developer receives when the plan is promoted

references/story-examples.md · Example 1
Add a practitioner to base and child networks at an approved location

Persona: Network Configuration Specialist · Domain: Network participation · Scenarios: NW-01, NW-02, NW-08 · Volume: tens per day, up to 40 rows per save

Org Discovery Context (extract)

#FindingProvenance
D-1HealthcareProvider, one per practitioner[Discovered]
D-4HealthcareFacilityNetwork per practitioner-location-network; child networks via the payer network's parent[Discovered]
D-5IsActive + effective dates; a scheduled job activates future-dated rows[Discovered]
D-12Directory and claims read participation nightly[Assumed — confirm]

The Story

As a Network Configuration Specialist, I want to add a credentialed practitioner to a base network and its child networks at an approved location in one action, so that participation is complete and correct before the effective date and the directory and claims see it on time.

AC-1 — Pattern A

Given a Network Configuration Specialist is working a credentialed practitioner at an approved practice location
When they add the practitioner to a base network with an effective date next month
Then participation is recorded for that location in the base network and in each of its child networks from that date
And none of the new participation is shown in the provider directory before that date

AC-2 — the negative case is mandatory

Given the practitioner already participates in a network at that location for an overlapping period
When the specialist adds the same network and location again
Then the save is blocked (blocks)
And the specialist sees the existing participation and its dates

AC-5 — Pattern E, every field

Network participation (base) — Create [Product: HealthcareFacilityNetwork]: payer network, practitioner facility, healthcare facility, healthcare provider, account, effective from, effective to (the earlier of the entered end date and the location's end), active (false until effective from), panel status, panel limit, directory display [Proposed]. Then one child row per child network, each field stated.

PersonaPattern APattern DPattern EA-2 · A-3A-5Effort

Technical Implementation (high-level)

After the criteria: each component with its provenance and the ACs it implements — the product participation object, a [Proposed] directory-display field, a [Proposed] participation grid and bulk service, and the [Discovered] scheduled activation job, unchanged.

Condensed from the worked example shipped in the package. The full story, including Definition of Done, Clarification Questions, Impact Analysis and effort, is in references/story-examples.md.

What the agent asks before it writes anything
The agent handles
  • Detecting the workflow mode from your phrasing
  • Running Org Discovery to the depth the mode needs
  • Selecting lifecycle domains, scenarios and their edge cases
  • Verifying every name, or labelling it proposed or assumed
  • Walking the build ladder and stating the volume class
  • Checking for overlapping stories — or saying it could not
You still decide
  • The persona and the business outcome
  • Provider types, lines of business, states and networks in scope
  • Compliance scope: accreditation, delegation, program rules
  • Which validations block and which only warn
  • Who approves, and whether the estimate is credible
Review checklists 0 / 6

Before the product owner sees a plan or prototype

  • The Org Discovery Context table is at the top, every finding labelled
  • The prototype banner names the build technology and the rejected alternative
  • Every button, input, grid and card carries a badge
  • Every custom element shows [Proposed] or its discovered source
  • Unknown values are shown as {… per D-n}, not invented
  • The volume class is stated and the volume rule applied

Before a story goes to refinement 0 / 6

  • A concrete persona — no "user", "system" or unqualified "admin"
  • Every behavioural criterion is Given / When / Then with one When
  • At least one negative criterion, each validation marked blocks or warns
  • A Pattern E table for every record written, every field listed
  • Compliance & Audit present if credentialing or termination is in scope
  • Downstream consumers listed, or raised as a Clarification Question

Install once, then work in plain language.

The Pattern

Publish once, install everywhere

One owner maintains the skill; everyone else pulls it down — the same mechanism the team already uses for shared libraries.

git clone https://github.com/p-kothapalli/pnm-delivery-architect.git
cp -R pnm-delivery-architect/.cursor/skills/pnm-delivery-architect ~/.cursor/skills/
cp pnm-delivery-architect/.cursor/rules/use-pnm-delivery-architect.mdc ~/.cursor/rules/
What publishing looks like — three steps
1
Fork or mirror the repositoryKeep the skill, the trigger rule, the evaluations and the validator together. The evaluations are how the next maintainer knows a change was safe.
2
Run the validator in CIEvery change runs the package checks, so a broken reference or a missing evaluation is caught before anyone installs it.
3
Share the install and the checkpoint promptClone, copy, reload, run the checkpoint. That is the whole onboarding ask — no per-person setup session.
Working practices

Do

Keep engagement specifics — prefixes, role titles, status values, tool bindings — in the workspace adapter. Fix gaps in the shared references so every engagement benefits, and add an evaluation for each fix.

Avoid

Don't fork the skill for one engagement — divergent copies drift apart and lose the protection of the evaluations. Keep examples on the placeholder prefix and fictitious data.

Keep it healthy

Each Salesforce release — product claims

PromptReview the PNM product baseline, the object catalog and the source register against the current release. List every object or field page whose verified date is older than the latest release, re-verify what you can against official documentation, and mark the rest as not verified with today's date.

Quarterly — run the evaluations

PromptRun each evaluation in the skill's evaluations folder against its fixture. Score every expected_behavior item Pass, Partial or Fail, check every must_not item, and report which hard blockers failed and in which mode.

After a gap is found — extend the library

PromptWe hit a PNM scenario the library does not cover: [describe it]. Propose a scenario ID in the right domain, a card with basis, evidence, discovery dimensions and edge cases, and an evaluation with a fixture that would have caught the gap.

Every change — validate

Terminalpython3 .cursor/skills/pnm-delivery-architect/tools/validate.py --strict

Evaluations are the source of truth for whether the skill still works — extend them before extending the documentation.

None is required. Bindings are recorded in the workspace adapter by capability, so the skill never depends on a particular tool being installed.

What the skill will not do — by design

  • It plans; it does not build. Writing metadata or code is out of scope — the output is what a builder needs to start.
  • It never executes data changes. Remediation produces rules, evidence and validation queries for people to run.
  • It does not assume an organisation. With no discovery and no adapter, names stay proposed or assumed, and the gaps become Clarification Questions.
  • It is honest about its own state. Product facts carry verification dates, unverified catalog pages are marked, and the evaluations in v1.1 are written but not yet scored in live sessions.
